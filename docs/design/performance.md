# Performance-driven development

Ofir's goal is to be fast, both the compiler and the programs it produces.
Performance is therefore **measured continuously** and every change is
judged by data, not by intuition.

## 1. What is measured

| Metric | Tool | Use |
|--------|------|-----|
| Instructions executed | `valgrind --tool=cachegrind` | **regression gate**: deterministic, reliable on shared CI machines |
| Wall time (median of 5 runs) | `bench/run_bench.py` | human-readable speed, lines per second |
| Peak memory (max RSS) | `os.wait4` | memory budget |
| Time per phase | `ofir build --time-passes` | where a single compilation spends its time |
| Hot functions | `valgrind --tool=callgrind` + `callgrind_annotate` | what to optimize next |

Later milestones add: the size of generated binaries (M1), the speed of
generated code against C, Rust and Go baselines (M2 onward), and the time
the compiler takes to build itself (M4).

`make bench-programs` measures generated Ofir programs against optimized C,
Rust and Go implementations of the same workloads. The runner verifies outputs
before timing and records toolchain versions in
`build/generated-code-results.json`. CI uploads this file as an artifact; copy
results from a fixed machine into `bench/HISTORY.md` for each release.

## 2. Benchmarks

`bench/run_bench.py` runs each benchmark on inputs generated by
`bench/gen_source.py` (deterministic, realistic code: functions, structs,
expressions, strings with interpolation, comments).

| Benchmark | What it measures |
|-----------|------------------|
| `lex-10k`, `lex-100k` | lexer throughput (`--stop-after=lex`) on 10 000 and 100 000 lines |

Each new compiler phase adds its benchmark when it is written
(`parse-100k`, `check-100k`, `build-100k`, ...), using `--stop-after=<phase>`.

## 3. Workflow

```
make bench                       # measure the working tree
make bench-compare BASE=main     # compare with another revision
ofir build file.of --time-passes
valgrind --tool=callgrind build/release/ofir build big.of --stop-after=lex
callgrind_annotate callgrind.out.* | head -30
```

1. **Measure before optimizing.** Profile with callgrind and pick the
   largest cost; do not optimize what the data does not show.
2. **One optimization per commit**, with a `perf(...)` commit message that
   states the measured effect on the benchmarks, e.g.
   `lex-100k: -59.5% instructions, -38.6% wall time`.
3. **Record** the new numbers in [`bench/HISTORY.md`](../../bench/HISTORY.md)
   for every `perf` commit and at every milestone.

## 4. Regression gate

On every pull request, CI (`.github/workflows/bench.yml`) builds the base
branch and the pull request in release mode and compares them:

- an instruction count increase above **3%** on any benchmark fails the
  check;
- a justified regression (a new feature that must do more work) is accepted
  by stating it in the pull request; the new numbers become the baseline.

Wall times are printed for information only, since shared runners are noisy.

## 5. Targets

| Metric | Target | Current (bench/HISTORY.md) |
|--------|--------|----------------------------|
| Lexer throughput (stage 0, release) | ≥ 2M lines/s | ~2.1M lines/s |
| Front end, lex → borrow check | ≥ 200k lines/s per core | — |
| Self-compile, debug build | < 5 s | 16.9 s cold, 1.4 s warm (§6) |
| Generated code vs `clang -O2` C | within 10% | — |
| Hello world binary (stripped) | < 50 KB | — |
| Compiler peak memory | < 20× the source size | ~8.5× (lexer only) |

## 6. Build times

The object cache of [ADR 0033](../adr/0033-codegen-units.md) keys each
codegen unit, one per module, by its LLVM IR text, the clang flags, the
clang path and `clang --version`. The text holds every type layout, constant
and signature the unit uses, so a key changes exactly when the object would:
`tools/check_object_cache.py` edits a copy of a program and checks that an
edit that changes no code (a comment) compiles no unit, a new function body
compiles its own unit, and a new struct layout compiles its module and the
module that uses the type. The same script covers recovery: a cached file
that is not an object is compiled again, and a link that fails with cached
objects is retried without them.

Self-compile of `compiler/main.of` with stage 1 (debug build, 4 cores,
`--time-passes`):

| Build | Units compiled | Objects | Total |
|-------|----------------|---------|-------|
| Cold (empty cache) | 123 | 15.6 s | 16.9 s |
| Warm (nothing changed) | 0 | 0.01 s | 1.4 s |
| One function body edited (`air/validate.of`) | 1 | 0.04 s | 1.3 s |
| Release, cold (one unit) | 1 | 103.7 s | 104.7 s |
| Release, warm | 0 | 0.01 s | 1.1 s |

A warm build is now the front end: parsing, checking, lowering and codegen
take about 1.2 s and run on every build. Caching their results is out of
ADR 0033's scope, so it waits for a measured need; a release build stays a
single unit so the optimizer sees the whole program.
